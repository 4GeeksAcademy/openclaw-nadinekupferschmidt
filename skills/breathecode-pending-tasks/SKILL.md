# BreatheCode: estado de proyectos por tarea única

Usá esta skill por defecto para que Nadine consulte sus proyectos únicos pendientes de entregar, con correcciones o esperando revisión, aunque cada proyecto aparezca en varios cohortes. Si pide explícitamente lecciones o ejercicios, incluí también esos tipos junto con los proyectos; no incluyas otros tipos salvo que los pida.

## Procedimiento

1. Usá exclusivamente la variable de entorno `FOURGEEKS_TOKEN`. Nunca leas archivos de secretos, muestres, registres, copies, guardes o incluyas el token en la salida.
2. Hacé únicamente peticiones de solo lectura a `GET https://breathecode.herokuapp.com/v1/assignment/user/me/task`, con `Authorization: Token ${FOURGEEKS_TOKEN}`. No sigas redirecciones a otro host.
3. Por defecto, consultá únicamente `task_type=PROJECT`. Si Nadine pide explícitamente lecciones o ejercicios, agregá `LESSON` o `EXERCISE` según corresponda, manteniendo `PROJECT`; excluí los demás tipos. Para cada tipo solicitado, recuperá registros de `task_status=PENDING` y de `task_status=DONE` para cada `revision_status` conocido: `PENDING`, `APPROVED` y `REJECTED`. Usá `task_type`, `task_status` y `revision_status` como filtros. No consultes endpoints adicionales.
4. Usá `limit` y `offset` para paginar. Respetá el esquema de paginación que devuelva la API; si no indica páginas siguientes, avanzá el offset por el límite y detenete cuando una página tenga menos elementos que el límite. Evitá repetir offsets y limitá la paginación ante respuestas inconsistentes.
5. Capturá respuestas y códigos HTTP en memoria. No imprimas cuerpos crudos, encabezados, token ni detalles de transporte; no uses modo verbose ni trazas que puedan revelar credenciales. Agrupá todas las apariciones por `associated_slug`, que es la identidad de la tarea. De cada aparición extraé tipo, título, `task_status`, `revision_status` y nombre de cohorte (`cohort.name`). Deduplicá repetidas apariciones del mismo `associated_slug` dentro de los resultados; conservá para el análisis los estados y cohortes distintos asociados a ese slug. Si falta `associated_slug`, no lo fusiones con otra tarea: señalá que el registro no se pudo identificar de forma fiable.
6. Clasificá cada `associated_slug` una sola vez y con esta precedencia: (a) si hay alguna aparición `DONE` con `revision_status=APPROVED`, considerala aprobada y no la incluyas en ninguna categoría solicitada; (b) en otro caso, si hay alguna aparición `DONE`, nunca la cuentes como pendiente de entregar; si entre sus revisiones hay `REJECTED`, clasificala «Requiere correcciones»; si no hay `REJECTED` y hay `PENDING`, clasificala «Entregada, esperando revisión»; (c) solo si no hay ninguna aparición `DONE` y existe al menos una `PENDING`, clasificala «Pendiente de entregar». Para esta última, mostrá el nombre de los cohortes donde figura como pendiente. Las demás combinaciones no se infieren; reportá cualquier estado no reconocido aparte si corresponde.
7. Mostrá los proyectos agrupados en las categorías «Pendiente de entregar», «Requiere correcciones» y «Entregada, esperando revisión». Cada proyecto debe aparecer una sola vez; incluí el nombre del cohorte o los cohortes relevantes junto a cada proyecto. Calculá al final los totales por categoría y el total de tareas únicas, contando cada `associated_slug` una sola vez. No sumes varias apariciones/cohortes como proyectos diferentes.
8. Si la respuesta es HTTP 401/403, informá que el token no es válido o no tiene acceso. Para fallos de red, respuestas inesperadas o errores del servidor, indicá que no se pudo consultar; no afirmes que el token es inválido. Si no hay resultados, decí claramente que no hay proyectos en las categorías solicitadas y que el total es 0.
9. No hagas operaciones de escritura ni consultes datos adicionales fuera de este endpoint.
